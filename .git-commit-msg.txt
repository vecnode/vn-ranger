Add quarantine with a verified restore and an irreversible purge

Wave 2, first half (docs/PLAN.md §6.10): the first code in ranger that can
destroy something, and the first that can put it back.

- an entry is `quarantine/<id>/` holding `manifest.json` and `payload`. The
  manifest is written and synced before the payload moves, so an entry that can
  be seen can always be described.
- `take` identifies the file, derives the id from its hash, path, moment and
  attempt, writes the manifest, re-checks the identity and moves. A payload
  whose hash does not match after the move is a refusal, and the entry stays so
  a recovery verdict can find it.
- `restore` verifies the payload against the manifest, refuses a mismatch,
  refuses an occupied destination, and puts the file back with a hard link:
  the portable create-only-if-absent, where a rename would replace. Only then
  does it remove the stored copy and the entry.
- `purge` is the one irreversible act: an id inside the quarantine root, the
  payload, the manifest, then the directory.
- `finish_entry` takes the entry by value, because on Windows an open handle to
  a directory prevents removing it, and the error says access denied, which
  tells a person nothing.

Tests: a round trip returns the same bytes and clears the entry; a tampered
payload is refused and nothing is written back; a file that reappeared is not
overwritten; a path-shaped id never reaches the filesystem; a collision lands
on a second entry rather than an error.

Not wired to the journal or the interface yet: the Act surfaces, the intent and
result lines and the recovery list are the next step, so no user-facing act can
be triggered before it is journalled.

Tests: 78 core, 44 native, 7 interface.
